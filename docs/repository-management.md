# 仓库文件管理规范

适用项目：彩条提取工作台（livery-lab）。生效日期：2026-10-19。

目标是让源码、长期资料和可再生文件各有固定位置，避免每次 AI 修改都增加一批无法判断用途的文件。本规范从新增文件开始执行，现有文件逐步整理，不要求为统一目录立即重构工程。

## 1. 目录与提交规则

下表中的 `docs/`、`scripts/`、`tests/` 是新增文件的固定位置，按实际需要创建子目录，不创建空占位文件。

| 位置 | 存放内容 | Git 管理 |
| --- | --- | --- |
| 根目录现有 `app.py`、`ui.py`、`engine.py` 等 | 当前入口及业务模块，修改时就地维护 | 提交 |
| `core/` | FS 解析等核心模块 | 提交 |
| `docs/` | 长期维护的架构、开发、操作与维护文档 | 提交 |
| `scripts/` | 可重复使用的开发、诊断、构建及维护脚本 | 提交 |
| `tests/` | 新增自动回归测试，命名 `test_<feature>.py` | 提交 |
| `tests/fixtures/` | 测试必需的小型、脱敏输入 | 审查后提交 |
| `reference_library/` | 运行时使用的参考素材 | 保留当前规则，不混入运行结果 |
| `research/<topic>/` | 仍有价值的解析研究、实验实现和说明 | 选择性提交源码及必要资料 |
| `validation/<topic>/` | 可审阅的验收结论、脱敏指标与必要对照样本 | 选择性提交；不提交整批结果 |
| `.local/tasks/YYYYMMDD_topic/` | 一次性脚本、日志、截图、接口调试、批量实验结果 | 不提交 |
| `.local/backups/YYYYMMDD_topic/` | 本地配置及修改前备份 | 不提交 |
| `output/` 或用户指定位置 | 应用生成的 SVG、PNG、manifest、report 等完整任务成果 | 不提交 |
| `build/` | 打包中间产物 | 不提交 |
| `release/` | 可运行的发布包 | 不提交；单独管理交付 |
| `settings.json`、`.api-key.dpapi`、`.env` | 本机配置及凭据 | 不提交 |
| `settings.example.json` | 脱敏的共享配置模板 | 提交 |

现有根目录 `test_*.py`、`ui_README.md` 和工具脚本暂时保留，以兼容当前命令及引用。新增同类文件按上表存放；不要为了“整理”直接移动全部源码。

## 2. 每次 AI 任务的固定流程

1. 阅读根目录 `AGENTS.md`，检查 `git status --short` 和相关目录，识别已有修改。
2. 确定每个新增文件属于业务实现、长期测试、长期文档还是临时产物；先选目录，再创建文件。
3. 优先改已有实现。新功能模块放在已有职责目录；确需新增根目录模块时，在交付说明中解释原因，避免借本次任务扩大重构。
4. 一次性调试统一使用 `.local/tasks/YYYYMMDD_topic/`。例如 `.local/tasks/20261019_vision_proxy/probe.py` 与 `results/`；同一任务不另建多个根级输出目录。
5. 临时脚本验证出需要长期防止的缺陷时，将有价值的断言整理进正式回归测试，再清理临时脚本。不要把真实接口联调脚本直接当作默认单元测试。
6. 只保留本次任务必要的验收摘要，检查敏感信息，清理本次产生的无用文件。
7. 检查最终差异及未跟踪文件；交付时说明修改内容、验证结果、文件位置和清理范围。

用户成果有版本历史需求时，沿用程序现有的版本化输出机制；不要为人工整理改变程序的缓存、事务或导出语义。

## 3. 命名与文档归档

- 长期脚本、测试和模块使用清楚的功能名，例如 `tests/test_vision_transport.py`，避免 `temp.py`、`test2.py`、`fix_final.py`。
- 文档允许中文标题，文件名保持稳定；同一主题更新原文档，不反复新增“最终版”“最新版”“修复版”。
- 日期仅用于临时任务、维护记录或发布目录；功能文档、正式模块与回归测试不以日期区分版本。
- README 说明运行方法和当前能力，并链接详细文档。长篇排查过程放在对应专题；避免持续追加本机地址、模型切换记录和配置备份路径。
- 新验收目录使用稳定主题名，例如 `validation/vision_transport/`；在说明中记录日期和版本，不为每次重跑建立一套可提交的目录。

## 4. 验收资料与大文件

保留足够支持结论的证据，而不是所有中间结果。验收说明应包含：问题或目标、代码版本或工作区状态、执行命令、输入来源及摘要、通过与失败情况、已知限制。

保留的 JSON 或日志必须去除令牌、授权头、个人目录及不必要的服务端信息。模型原始响应、FS 原件、整套候选图集、大型场景 JSON 和重复渲染图默认留在本地临时目录。确为重现所必需时，提炼最小样本并说明来源及用途。

`research/` 中已有研究资料、`validation/reference_audit/`、`validation/reference_exports/`、组件研究记录和 `reference_library/` 不因“看起来是输出”就批量删除；其中包含历史依据或运行依赖。

清理后保留的历史报告仅代表当时的结果。报告引用的本地完整运行目录可能已经删除；不应宣称这些报告对应当前代码已重新验证。

## 5. 测试管理

当前根目录测试包含解析、事务、界面预览、并发、代理、重试和流式响应等回归检查，不按文件数量判断是否多余。

从仓库根目录运行现有测试：

```powershell
python -X utf8 -m unittest discover -s . -p "test_*.py" -v
```

开始新增 `tests/` 下的测试时，创建 `tests/__init__.py`，保证根目录 unittest 发现流程能够递归发现；测试通过正常模块导入访问项目代码。测试临时文件使用 `tempfile.TemporaryDirectory()` 并自动释放，不固定写入根目录。

需要真实 FS、界面显示或网络的测试应说明运行条件。真实 AI 联调单独显式执行，不能作为普通回归测试的默认收费步骤。现有测试迁移到 `tests/` 时，必须同步维护 README 中的模块运行命令及相关依赖，并验证测试数量没有减少。

## 6. Git 与清理边界

- `.gitignore` 管理可再生内容和私密内容，不用于掩盖本应修复的源码变更。已经跟踪的文件不会因为新增忽略规则自动退出 Git。
- 提交前查看 `git diff --stat`、`git diff --check`、`git status --short`，并检查待提交的具体文件。暂存使用明确的文件路径，避免混入其他任务的工作。
- 不创建源码 `.bak`、复制整个工程或生成 `engine_new.py` 保留历史；源码版本交给 Git。本机配置备份放 `.local/backups/`。
- 递归删除前验证绝对路径位于当前仓库内，检查符号链接或目录联接及 Git 跟踪状态；对含义不明的文件先核查引用和内容。
- 测试缓存、废弃构建和本次任务生成的临时文件可在任务结束时清理。用户导出成果及可用发布包即使被忽略，也不能视为自动可删。
- 不自动执行 `git clean -fdx`、`git reset --hard` 或批量清空未跟踪文件。删除源码和已跟踪验收资料须有明确依据。
- 清理只删除已核实的目标；报告删除数量、大小和保留内容。不自动提交或推送。
