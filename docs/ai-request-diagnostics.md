# AI 请求诊断与 Qwen 调优

适用于新版源码的六类提取。重启源码应用后重新提取才生效；旧 EXE 不会因源码修改自动升级。

## 查看实际请求

主界面选中已处理文件，点“AI 请求明细…”。表格逐批显示阶段、候选数、HTTP 次数、耗时和图片尺寸；选中一行可查看完整发送参数、提示词和接口返回的 token 用量。

每个任务的版本目录保留 `ai_requests.json` 汇总和 `ai_requests/*.json` 逐请求记录，清单也提供汇总路径。成功及失败的请求都会记录；`accepted` 只表示协议验收通过，不表示分类正确。正在执行的请求是 `running`，不计作失败。传输重试在同一请求的 `attempts` 中，补查、冲突复核和协议补问是新的模型请求。

记录包含候选编号、图片尺寸/字节数/哈希、完整提示词、实际请求参数、耗时、结束原因、模型返回名称、分类数量及 HTTP 状态。**不记录密钥、接口地址、授权头、图片 base64、模型原始响应或思考内容**。提示词包含原稿的候选元数据，分享前仍应审阅。服务端没有返回的用量标为未知，不能当作零。

离线比较两个任务：

```powershell
python -X utf8 scripts/inspect_ai_requests.py "任务A的版本目录" "任务B的版本目录" --output ".local/tasks/日期_诊断/request-comparison.md"
```

旧版结果没有逐请求记录，只能从 decision 文件推断业务阶段，不能补造历史 HTTP 重试、耗时或用量。

## 调整客户端

“AI 调优…”只保存本地配置，不调用接口；重新提取后生效。双窗口对比的设置互相独立。单窗口快捷切换会读取对应 `.local/ai-profiles.json` 的调优字段，缺省使用以下默认值。

| 配置 | 默认 | 含义 |
|---|---|---|
| `component_batch_size` | `auto` | 模型名含 Qwen 时每批 12 个；其他模型 0，整张提交。可用 0–120 的整数覆盖。 |
| `component_concurrency` | `1` | 同一文件首轮分类、空结果恢复及残留面复核的同时请求批次数，范围 1–3；2 表示最多两批并发。不同阶段仍依次执行，冲突与一致性复核保持串行。 |
| `prompt_style` | `auto` | Qwen 使用 `compact`，其他模型使用 `detailed`；可显式覆盖。 |
| `max_output_tokens` | `0` | 0 不发送；正数作为 Chat Completions 的 `max_tokens`。与上下文窗口不同。 |
| `reasoning_effort` | 空白 | 不发送，沿用服务端默认；非空仅支持 low/medium/high，需接口兼容。 |
| `temperature`、`top_p` | `null` | 不发送，沿用服务端默认；没有为本次任务强行改采样参数。 |
| `include_usage` | `false` | 启用时发送 `stream_options.include_usage=true`，需接口支持。 |

Qwen 的 compact 模式：两列图集，每个候选保持 400×190 的显示格；首轮及残留面补查均按区域分批。新版另附原稿局部及候选定位对照图，补查再显示当前车漆，辅助检查完整性。保留整车上下文和原 G 编号；使用逐编号单标签协议，减少重复分类和长输出。完整原生组合可直接作为彩条候选；窗框、轮胎、灯具等需按用途排除。分类仍由模型判断，没有以文件名、颜色或编号硬编码答案。

漏答/未知标签以及正常结束的 compact 响应中的区域、方向等分类字段格式错误会拒绝该响应，并拆半补问；若仍有协议问题则继续拆小，最小到单对象，仍失败才终止并保存诊断。每次补问的候选数严格减少，批次路径保留完整拆分层级，绝不把漏答默认为“不提取”。传输、鉴权、截断或非 JSON 响应不会触发这种补问。不同非车身类别争用源路径时集中复核，未解决的候选保留给人工归类。调用更多并不保证准确率更高。

## 区域配套送审与车漆完整性复核

### 原生组合优先的两阶段识别

六类提取现在依次完成 `native_groups`（原生 `AGroup` / `AComposite` 整组识别）和 `local_members`（其余局部候选分类），随后沿用车漆完整性复核。每阶段独立校验；全部原生批次成功后才进入局部阶段，局部阶段继承已确认车身上下文和已选父组类别。Qwen 默认每批 12 个；未指定数量的其他模型或数量为 0 时，每阶段使用最多 20 个候选的区域批次。原生阶段使用独立短提示，明确灰度结构组也是车身、混合用途组不能整体当车漆，以及多块分离漆面应完整选取。批次并发只在同一阶段内运行。

120 项仍是初始候选预算，但达到大组保留条件、未被完整父组包含的原生组可额外入池，避免与生成候选争名额后丢失。未覆盖的细小组和未解析原语仍可能遗漏；不能将预算例外理解为完整支持所有 FS 对象。

父子源区间和已选父组类别随候选送审。跨阶段的不同非车身类别如争用源路径，会集中复核，仍冲突则留人工判断。车身组默认继承全部已解析成员，仅扣除明确分类的例外；`body_group_audit` 记录原始成员、保留成员和转类去向。人工导出的复核记录按实际最终选择重新计算，并列出人工未选成员。

车身 / 车漆按确认区域、相同来源方向默认合并导出；多个原生组或不相连源对象可属于同一个成品，保持原坐标、颜色、渐变和绘制顺序，不做几何布尔合并。区域不明、方向冲突或 `keep_separate=true` 时不合并。复核页可勾选“本次添加单独导出”，标记随复核记录保存。彩条、文字、logo、门徽不适用这项自动合并。

补查不再套用首轮 120 个候选预算：所有符合条件的残留提案均进入区域分批复核，已选车漆重审不再挤占补漏名额。未分页模型补查每批最多 20 个，分页模型沿用配置上限；因此复杂稿的调用次数和耗时可能增加。`body_surface_audit_eligible`、`body_surface_audit_candidates`、`body_surface_audit_omitted` 分别记录符合条件、实际入队和因队列上限遗漏的提案数；正常完整补查最后一项为 0。这不包括尚未解析、非闭合、样式不支持、低于局部面积门槛或没有车身区域归属的对象，不能等同于所有源对象均被审查。`paint_completeness_rechecked`、`paint_completeness_removed`、`paint_completeness_batches` 分别记录重审编号数、撤出车漆编号数和区域复核批数；编号数不等于去重源路径数。原稿局部边界和编号列表另存 `region_context.json`，真实发送图片尺寸/哈希及提示仍在 AI 请求明细中。

首轮和补查提示均明确：车顶空调罩、顶部长条外壳和前端斜面的基础填充可以是独立实色路径，不要求与侧面主底色同色、同渐变或包含完整车辆；其上叠加的轮廓、分缝和格栅仍是结构。该说明不按固定颜色、对象编号或文件名自动分类，仍须核对真实模型是否选全及有无误选。

完整补查后另做一次单对象一致性复核：已入候选池但仍未归入非车身类别的单路径面，如果位于已选车身区域，且与已选车漆有相同的非中性实色填充或相同渐变类型、色标，则单独发送原稿及局部移除对照。填充匹配仅用于召回复查，绝不直接赋予车漆标签；模型仍可判为彩条或不提取。渐变比较使用类型与色标，不要求不同视图的坐标矩阵相同。`paint_consistency_candidates` 记录额外复查的对象数，`paint_consistency_added` 记录模型明确补入的车漆源对象数。这一轮不会撤回已经确认的车漆候选，也不替代人工复核。

使用时重启新版，勾选六类提取和 AI，并强制重新识别此素材。旧 EXE 和已有结果不会自动升级。此次离线验证不代表 AI 准确率已提高；试验需比较前后小漆面召回、误选玻璃/灯具、完整图案、请求次数及耗时。

## 并发与原图缓存

单候选出现 `CompactLabelError` 时，最多再做两次带明确编号约束的纠错请求（单候选合计最多三次），仍失败才终止。网络、鉴权、非 JSON 和截断错误不计入这类纠错，不把无效回复当作“不提取”。

六类提取中校验成功的批次立即以原子写入方式保存在应用目录 `output/.cache/ai_batches/`。重启后重新提取也可复用；源文件摘要、程序及 AI 配置指纹、接口、请求阶段、提示词和实际输入图片必须一致。纠错成功结果与原请求共用检查点。缓存内容摘要及类别结构再次通过校验后才使用；损坏缓存重新请求。请求明细中的 `cache_hit=true` 表示复用，该记录的 HTTP 尝试数为零。失败的批次不保存，后续阶段继续依赖已验证的分类结果，不会跳过失败对象。

检查点从此版本开始生成，旧失败任务不能追溯恢复此前未保存的分类。强制重新提取仍可复用相同输入的批次；如需全量重新询问模型，可在关闭任务后将上述缓存目录移出。此机制保留已有人工复核及最终成果版本校验。

“AI 请求调优”可设置同时请求批次数，默认 1。并发仅重叠独立批次的模型等待，图片准备仍串行，结果按原批次顺序合并；不修改每批候选、提示词、图片分辨率、采样参数和全部补漏范围。协议修复在当前请求槽内递归，不额外扩张并发数；任何批次失败仍抛错，不把缺失响应视为未选中，也不提交该阶段的最终合并结果。多文件同时提取时，总请求并发可能达到文件并发数乘以批次并发数。

每次提取有独立、最多 32 MiB 的图片编码缓存；全景图复用相同源文件的编码，保留每批原有图片副本。图片编码缓存只省去本地重复读取和 base64 编码，每次实际 HTTP 请求仍发送完整原始图片。文件元数据变化时重新读取；跨任务复用分类结果由上述检查点另行校验。

请求日志并发读写使用同一进程内的锁，防止 Windows 上读取时替换文件造成冲突。`elapsed_seconds` 是各请求耗时之和，并发时不等于用户等待的墙钟时间；提速应比较整次任务起止时间。离线回放验证调度、请求正文和合并一致，不代表真实服务端在并发负载下的准确率或速度已经通过验收；启用两批并发后应保留原有人工复核。

## 128K 与思考模式

128K 是服务端上下文容量。客户端无法通过 `max_tokens` 把服务端窗口调大，也不能仅凭模型名称确认实际部署容量。窗口足够大，不代表缩成一张长图的 120 个图案仍然清晰。先检查每次实际输入、输出、结束原因及图片尺寸，再决定是否需要扩大服务端窗口。

2026-10-21 社内接口实测：发送 `reasoning_effort=high` 返回 HTTP 400，省略该字段后相同小样本可正常请求。因此本次配置将该字段留空。Qwen 已完成批次的接口用量报告 `reasoning_tokens=0`；这只能反映接口报告，是否禁用思考、是否正确映射模型参数，还需要服务同事核对网关与推理引擎。不能根据官方能力推定内部部署支持同名参数。

另做一次 `chat_template_kwargs.enable_thinking=true` 小样本探测：接口接受，但仍报告 `reasoning_tokens=0`，未观察到思考 token 增加。因此没有将此字段加入默认客户端配置；不能把 HTTP 成功当作已经开启思考。

同事排查时，可提供脱敏请求参数、输入/输出用量和结束原因；核查实际模型路由、thinking/chat template 设置、视觉预处理及视觉 token 限制、输出上限。先用同一小样本验证参数是否接受及是否改变报告用量，再扩大到整份文件。
