## 128K 和思考模式

Qwen 首轮每批报告输入 5002–5102 token，均正常 `stop`；没有上下文超限证据，故未调整服务端 128K。`max_tokens` 是请求输出上限，并非上下文窗口配置。

实际观察：

1. `reasoning_effort=high` 小样本请求返回 HTTP 400；省略该字段，相同图片和提示可成功。不能直接套用官方参数。
2. Qwen 本次各批报告 `reasoning_tokens=0`；Gemini 首轮输入 20904 token、思考 12842 token，补查报告思考 34317 token。报告字段来自各网关，统计口径可能不同。
3. 单独请求 `chat_template_kwargs.enable_thinking=true` 被接受，仍报告思考 0 token；没有将其加入默认配置。此观察不能证明参数被执行或服务端真实禁用思考。

服务同事应核对实际模型路由、thinking/chat template、视觉预处理与视觉 token 限制及输出上限。客户端增大输入窗口无法证明上述配置正确。

## 稳定性与排除实验

### 后续直接核查：接口声明 128K，整张输入实际可提交

同日用户提供接口信息后，直接查询 `/models` 和 `/models/qwen3.8-27b`，两者 HTTP 200，模型记录均声明 `max_input_tokens=131072`、`max_output_tokens=131072`。这确认网关对外公布 128K，但未执行接近 128K 的边界压力测试，也未取得推理进程的启动配置；不能将模型元数据当作后端满容量验证。

另将同源 120 个候选按原详细提示一次提交：主图集 1600×5700，另附原稿 1800×953、细节图集 1600×3800。一次 HTTP 成功，报告输入 33717、输出 2035、总计 35752 token，119.242 秒，结束原因 `stop`。因此这份完整输入确实可以提交，不需要因上下文容量而拆成多次请求。该测试显式设置输出上限 8192、请求用量返回，与历史未显式设置的请求不能当作完全相同条件。

此轮响应返回 8 个彩条组，但包括底漆父组 G114–G117，与同时归为车漆的 G046–G049 争用源路径；应用的源对象跨类校验拒绝该组合。原始彩条归类包含 68 条路径，相对本次 Gemini 对照多 31、少 1，预览可见大片蓝色底漆混入。**容量够、正常完成 JSON 输出，不代表分类结果可用。** 之前“Qwen 更适合分批”的说法只能作为当时的局部实验观察，不能据此判定整张请求必然差于分批。

脱敏元数据、逐请求用量及原始分类诊断留在 `.local/tasks/20261021_qwen_context_check/`；不含密钥或接口地址。当前接口没有返回图片处理像素/视觉 token 上限，不能认定长图实际被缩小；这仍需服务端配置或预处理日志确认。本轮没有修改应用默认分批设置或服务端配置。
